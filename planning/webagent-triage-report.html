Where a request breaks

The graph as built in backend/app/graph/workflows.py, with each problem placed where it stops or corrupts a run. Two problems act before the graph runs at all: B1 prevents LangGraph from importing, and B5 means an API request never starts the graph.

Recommended fix order

Each step makes the next one testable. Re-run test collection after step 2. Add the end-to-end test in step 3 before changing the agents, so you can see each fix take effect.

  1. Restore the Python environmentB1. Nothing that imports LangGraph runs until this is fixed.
  2. Unblock imports, prompts and the API’s background tasksB2–B5. Small edits. Expect zero collection errors from pytest --collect-only afterwards, and task IDs that resolve.
  3. Fix how agents pass state to each otherW1–W10. Start with one typed research plan and a scripted-LLM end-to-end test (see “The underlying cause”).
  4. Connect the web app to the backendF1–F3. Gives agentic mode a real path, makes production builds pass type-checking, and makes production chat match development.
  5. Harden before anyone else can reach itX1, X2 first, then S1–S4 and X3–X4.
  6. Clean the repositoryH1–H8, at any convenient point.

Critical: stops every run

All five were reproduced in the agents environment. The proposed edits for B2, B3 and B4 were checked against the real code. The B1 and B5 fixes are proposals and still need a test run.

B1

LangGraph won’t import in the “agents” environment

CriticalConfirmed

conda env “agents” · requirements.txt · backend/requirements.txt

Problem

from langgraph.graph import StateGraph fails with ImportError: cannot import name 'V' from 'langgraph.store.base'. The environment has langgraph 0.2.28 and langgraph-checkpoint 1.0.9 installed next to packages that need newer versions. pip check lists the conflicts:

  • langgraph-prebuilt 0.1.2 needs checkpoint ≥ 2.0.10
  • langgraph-api 0.0.27 needs langgraph ≥ 0.2.56 and checkpoint ≥ 2.0.15
  • copilotkit 0.1.39 needs langgraph ≥ 0.2.50

Files from checkpoint 2.x (store/batch.py, store/memory.py) now sit next to a 1.x store/base. This causes 9 of the 11 test-collection errors and breaks every integrated demo. Both requirements files use open-ended >= floors, so a fresh install can drift the same way.

Fix

Install one consistent set, then pin it:

conda run -n agents pip install "langgraph>=0.2.56,<0.3" "langgraph-checkpoint>=2.0.15,<3"
conda run -n agents pip check
conda run -n agents python -m pytest backend/tests --collect-only -q

If this project doesn’t use langgraph-api, langgraph-cli or copilotkit, uninstalling them is simpler than satisfying them. Then merge the two requirements files into one and pin exact versions, for example by freezing the working environment into a constraints file.

Not yet run. Watch for one behavior change: in LangGraph 0.2, invoking a graph returns a dict (see W6).

B4

Three agent prompts fail on every call

CriticalConfirmed

agents/supervisor.py SUPERVISOR_PROMPT · agents/team_manager.py TEAM_MANAGER_PROMPT · agents/data_analysis.py DATA_ANALYSIS_PROMPT

Problem

These prompts are built with ChatPromptTemplate.from_template, which treats every { as the start of a variable. The JSON example in each prompt creates a required input with a nonsense name. For the supervisor it is '\n "task_type"', alongside query. Nothing ever supplies it, so each call fails with a missing-variable error. The supervisor runs first, so every agentic run ends at step one. This is likely the “template error” the 2.9.9 changelog works around in the demos. The senior research prompt has no braces and is unaffected.

Fix

Double the braces around each JSON example. Confirmed: with {{ }}, query is the only variable and the braces print as single braces.

Output your analysis in JSON format with these fields:
- {+ {{  "task_type": "document_extraction" or "complex_research",
  ...
- }+ }}

Add a unit test asserting that each prompt’s input_variables match the keys its agent passes in.

B5

The API never runs the workflow, and the task and document endpoints fail

CriticalConfirmed

app/core/metrics.py:340–382 · app/utils/metrics.py (second copy) · services/task_manager.py:37 · api/endpoints/tasks.py · api/endpoints/documents.py

Problem

Both copies of timing_decorator wrap functions in a plain synchronous wrapper, and they are applied to async functions. The wrapper returns an un-awaited coroutine, and FastAPI and Starlette no longer recognise the function as async. Two failures follow, both reproduced with the repo’s own decorator:

  • The workflow never starts. TaskManager.run_workflow is decorated and launched with BackgroundTasks. Starlette treats it as synchronous, calls it in a thread, and drops the coroutine it gets back. The request returns a task ID, no task is ever recorded, and polling that ID returns 404 indefinitely.
  • Ten endpoints fail with an error. Every endpoint in tasks.py and documents.py (list, get, result, error, create, delete, upload, search and so on) is decorated. FastAPI tries to serialise the coroutine and raises ValueError: 'coroutine' object is not iterable.

Awaited agent methods such as TeamManagerAgent.run still work, but the timings recorded for them are about zero.

Fix

Make the decorator handle async functions, and keep a single copy of it (delete the one in app/utils/metrics.py and import from app/core/metrics.py).

def timing_decorator(func):
    if inspect.iscoroutinefunction(func):
        @wraps(func)
        async def async_wrapper(*args, **kwargs):
            start = time.perf_counter()
            try:
                return await func(*args, **kwargs)
            finally:
                _record_time(func.__name__, time.perf_counter() - start)
        return async_wrapper

    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            _record_time(func.__name__, time.perf_counter() - start)
    return wrapper

Add one API test that posts a chat request and polls until the task leaves “processing”. That test would have caught this.

Workflow wiring: agents and routers disagree

Found by reading the code. None of these could run while B1 and B4 were in place. Each one ends the run early or drops an agent’s output.

W1

The supervisor and the routers use different names for the research plan

HighFrom code

agents/supervisor.py (prompt) · graph/workflows.py:52–55, 91–92, 191–192, 428–429 · agents/web_research.py:138

Problem

The supervisor prompt asks for needs_web_research and needs_internal_research. The router and the research node read requires_web_search and requires_internal_knowledge. A third function, research_router, reads requires_internal_search. With the keys the prompt asks for, the router concludes that no research is needed and ends the run.

Fix

Define the plan once and convert the model’s reply into it inside the supervisor:

class ResearchPlan(BaseModel):
    requires_web_search: bool = True
    requires_internal_knowledge: bool = False
    questions: list[str] = []

Ask for exactly these keys in the prompt, parse the reply with ResearchPlan.model_validate(...), and have every router and agent read the plan through this model. Delete the unused research_router and get_research_router functions.

W2

The parallel research node calls the agents the wrong way

HighFrom code

graph/workflows.py:178–239

Problem

run_research_agents has three problems:

  • It calls web_research.ainvoke(state), but get_web_research_agent() returns a plain async function, which has no ainvoke method.
  • It reads result.get("state"), but the agents return a WorkflowState, not a dict.
  • It returns {"state": state}. LangGraph copies a node’s output into the state one field at a time, and state isn’t a field of WorkflowState. Even after the call is fixed, every result from this node would be silently dropped (confirmed in langgraph/graph/state.py, _get_state_key).

Both agents also receive the same state object and would write to it at the same time.

Fix
results = await asyncio.gather(
    *(agent(state.model_copy(deep=True)) for agent in selected_agents))
for r in results:
    for name, report in r.reports.items():
        state.reports.setdefault(name, report)
return state

W4

Senior research always ends the run, and its follow-up loop is never triggered

HighFrom code

graph/workflows.py:104–139 · agents/senior_research.py:224–225, 258, 267 · agents/web_research.py:100, 134 · agents/internal_research.py:1054

Problem

The router after senior research reads needs_more_research and ready_for_team_manager. The agent writes neither; it sets research_status and the context flags continue_research and research_complete. Both reads default to false, so the run always ends and the team manager never runs. The agent also sets state.final_report to a plain string, and the task manager then calls .get() on it. Iteration tracking is split as well:

  • Senior research counts in research_loops; web and internal research read research_iteration.
  • The feedback carries current_iteration; web research reads iteration.

As a result, the follow-up research prompts never switch on.

Fix
def senior_research_router(state):
    if state.error:
        return END
    if state.context.get("continue_research"):
        return "research"
    return "team_manager"

Delete state.final_report = synthesis, and use a single research_iteration key in every agent and in the feedback.

W6

The task manager reads the finished state wrong and reports empty answers as completed

HighConfirmed in LangGraph source

services/task_manager.py:82–106 · api/endpoints/frontend.py:112–128

Problem

The graph’s output is a list of state fields, so LangGraph’s read_channels returns a plain dict from ainvoke, not a WorkflowState (checked in the installed langgraph/graph/state.py and pregel/io.py). final_state.final_report then raises AttributeError and every task is recorded as an error.

A second problem appears once that’s fixed. The task manager sets the status to “completed” before checking whether a report exists. A run that ends without a report is stored as completed with the result {"error": …}. The web-app status endpoint then returns result.get("content", ""), which is an empty string, so the user sees a blank answer instead of an error.

Fix
result = await workflow.ainvoke(initial_state)
final_state = (result if isinstance(result, WorkflowState)
               else WorkflowState.model_validate(result))
if not final_state.final_report:
    task_info.status = "error"
    task_info.error = final_state.error or "Workflow ended without a report"

Set “completed” only after a report has been stored.

W5

The team manager can loop until the recursion limit

MediumFrom code

graph/workflows.py:141–176 · agents/team_manager.py:161–190

Problem

After data analysis or coding, control returns to the team manager, which asks the model again whether analysis or coding is needed. Nothing records that those steps already ran. A model that keeps answering “true” loops until LangGraph’s recursion limit; the 2.9.9 changelog describes this happening in a demo. In the opposite case the router ends the run, but the team manager only writes final_report when both flags are false, so the task finishes with no report.

Fix
if needs_analysis and "data_analysis" not in state.reports:
    return "data_analysis"
if needs_coding and "coding_review" not in state.reports:
    return "coding_assistant"
return END

Put the same check in the team manager and have it write final_report whenever the router is about to end.

W7

Requests with agentic mode off, and document requests, end without a report

MediumFrom code

graph/workflows.py:71–74, 314–315 · agents/document_extraction_agent.py:646–704

Problem

With agentic_toggle off, the graph ends right after the supervisor without writing final_report, and the task manager records “Workflow did not complete successfully”. The document branch requires state.inputs["document_id"], which no API endpoint sets. It also writes its result to state.output instead of final_report.

Fix

When agentic mode is off, either answer in a single model call (a small node that writes final_report) or reject the request at the API with a clear message. Let the chat request carry document_id into inputs, and have the extraction node write final_report with a title and content.

W8

Workflow logs written by routers are discarded and never reach the report

MediumConfirmed in LangGraph source

graph/workflows.py:60–176 · models/task.py (add_log, mark_completed) · tests/test_workflow_logs.py

Problem

Most workflow logs, the feature added in 2.9.6, are written with state.add_log(…) inside the routers. LangGraph gives each router a fresh copy of the state, built with fresh=True in _get_state_reader, and keeps only the branch name the router returns. Every log line a router writes is thrown away. The only node that writes logs is the research node, and its output is dropped (W2). Separately, WorkflowState.mark_completed, the method that copies logs into the final report, is never called anywhere. The tests don’t catch this because their mocked agents write logs directly and don’t go through the real routers.

Fix

Write logs only inside nodes. Have the team manager, and any node that ends the run, call state.mark_completed(final_report) instead of setting final_report directly. If a log entry is needed for each routing decision, record it in the node that runs just before the router.

W9

The final report is the team manager’s raw JSON, and code review results are dropped

MediumFrom code

agents/team_manager.py:107–110, 178–190 · agents/coding_review.py:217

Problem

The team manager prompt tells the model to reply with a JSON object. The code then puts that reply text, unchanged, into final_report["content"], so the user would see a block of JSON instead of a written report. The team manager also never reads reports["coding_review"]. When the review agent fixes broken code, the report still shows the original code from the coding assistant.

Fix

Build the report text from the parsed fields (summary, analysis, recommendations, sources) as Markdown. Prefer coding_review.fixed_code when its fixed run succeeded, and include the review’s explanation.

W10

Earlier chat messages are ignored

LowFrom code

api/endpoints/frontend.py:59 · models/chat.py (session_id)

Problem

The web-app endpoint saves earlier messages in context["previous_messages"], but no agent reads them, and ChatRequest.session_id is never used. Each agentic request is treated as a new conversation, so follow-up questions such as “what about Europe?” lose their meaning.

Fix

Pass a short summary of the earlier messages to the supervisor prompt, so it can rewrite a follow-up question into a self-contained query before planning.

The underlying cause

W1 through W9 share one cause. Agents pass data through free-form dicts (state.context and state.reports), so a misspelled key reads as a silent default instead of raising an error. The demos never caught this because they wire their own small graphs around one or two agents. The existing workflow tests didn’t catch it either: they replace agents with mocks that write whatever the test expects, and those mocks return the same {"state": state} shape that LangGraph ignores.

Two changes would catch this whole class of bug:

  • Typed hand-offs. Give each agent a Pydantic output model (ResearchPlan, ResearchFindings, SeniorReview, TeamReport). Routers then read typed fields, so a wrong name fails when the code runs instead of returning a silent default.
  • One end-to-end test with a scripted model. Patch app.services.llm.get_llm to return LangChain’s FakeListChatModel with one prepared reply per agent. Run the full graph, and assert the order of visited nodes and that final_report has content. It needs no API keys and runs in seconds.

Web app integration

F1

Agentic mode in the web app never reaches the LangGraph backend

HighFrom code

next.config.js:45–58 · vercel.json · backend/api/index.py:48–104 · src/utils/apiClient.ts:440–600

Problem

In development, /api/task is forwarded to a Flask app on port 5000. Its task handlers return fixed placeholder text, and the FastAPI backend on port 8000 is never called. In production, vercel.json sends /api/task to the same placeholder. Even with the right target, the two sides don’t match:

  • The client sends only {query, image}, so the backend would see agentic mode as off.
  • The client starts polling only if the reply text contains “task_”, then uses the entire reply text as the task ID.
  • The client checks for status “failed”, but the backend reports “error”.
  • The backend’s web-app routes are mounted at /api/v1/v1/… because a /v1 prefix is applied twice.
  • Polling stops after 30 attempts, about two minutes, which a full research run can exceed.
Fix

Add a small task endpoint to FastAPI that matches what the client expects, and point the dev proxy at http://127.0.0.1:8000/api/task/:path*.

# backend/app/api/endpoints/task.py, mounted at /api/task
@router.post("")
async def create_task(req: TaskRequest, bg: BackgroundTasks):
    task_id = str(uuid4())
    bg.add_task(task_manager.run_workflow, task_id, req.query,
                {"agentic_toggle": True})
    return {"task_id": task_id, "status": "processing"}

@router.get("/{task_id}")
async def task_status(task_id: str):
    status, result = task_manager.get_task_status(task_id)
    return {"status": "failed" if status == "error" else status,
            "result": result}

In apiClient.ts, poll when response.task_id is present instead of matching on the reply text, and replace the 30-poll cap with a deadline of several minutes. Drop the extra /v1 prefix in api/router.py.

F3

MediumFrom code

vercel.json routes · backend/api/chat.py · src/app/api/chat/route.ts

In development, /api/chat is served by the Next.js route, which adds the system prompt, prompt style, knowledge focus, citation setting and image content. Security

These matter as soon as the backend is reachable by anyone other than you. A scan of tracked files and the full git history found no committed API keys. X1

Model-written code runs directly on the server

HighFrom code

agents/coding_review.py:270–360

Problem

execute_python_code writes the generated code to a temp file and runs it with the server’s own Python interpreter. The only limit is a 30-second timeout. That code comes from a chain that starts with web search results, so a hostile web page could steer it. That path runs from prompt injection to arbitrary code on the host.

Fix

Run generated code in a throwaway container with no network, a read-only filesystem, and memory and CPU caps, for example docker run --rm --network none --memory 512m --cpus 1 …. Until then, turn code execution off when running as an API server and keep it for local demos only.

X2

The API has no authentication

HighFrom code

app/core/security.py · app/core/config.py · backend/main.py

Problem

setup_security is never called. JWT and API-key checks are off by default, and no route requires credentials. SECRET_KEY falls back to insecure_key_for_dev_only_change_in_production. Anyone who can reach port 8000 can start paid model runs and upload documents.

Require an API key on the whole router with APIRouter(dependencies=[Depends(require_api_key)]). Make the server refuse to start in uat or prod while SECRET_KEY has its default value.

S3

MediumFrom code

services/llm.py:628–715 · agents/senior_research.py:85 · agents/data_analysis.py:63

Problem

The fallback order lists Groq, Anthropic and Gemini, but get_llm has no code for them, so they are skipped without any error. Read each agent’s model from the agents: block in the YAML config. That block already lists a model and temperature for every agent, but only the coding agents read it, and only for allowed libraries and the timeout. Pass a model name only to the provider it belongs to.
